# P04 個人食品補給の候補確認 — 0.4.13

2026-10-09。Core7／Colony1／World1／protocol2。製品へ統合し、同じ最終DLLで36試験（基本19／四DLC17）、日英9画像を確認した。保存形式は変更せず、食品を実際に補給する機能はまだない。証拠はEvidence/P04DelegatedSupplyPreviewの47ファイルへ保存。

独立レビューで、保存用の古い台帳を比較する点と、比較前のSaveSnapshotがcountを正規化する点を修正した。現在の台帳と生のColony状態を直接比較し、照会の基準を描画まで使い回す。その設計で実ゲームの無変更を測定した範囲だけを確認済みとする。

## 今回の機能

委任地点で保管中の一人または一頭について、元入庫に記録された同じ実在キャラバンが持つ食品を読み、持主・数量・食べ手ごとの単位栄養・合計栄養・日需要を表示する。元隊列は厳密なID一致で探し、別隊列や遠隔在庫へ自動で差し替えない。画面は候補確認専用であり、食品を移すボタンや食品の予約はない。

Coreの既存 `CheckResident`、`DailyDemand`、`PlainFood` と本体の `FoodUtility.NutritionForEater` を共用する。特殊な有効 `Gene_Resource`、薬物・遺体・摂取時の追加結果など、既存の通常食品会計が対応しないものを新しい画面だけで許可しない。未知の需要や栄養は「不明」と表示する。

照会にはCoreがreadyな世界とゲームスレッドが必要で、IDや証、保存行を割り当てない。snapshotの一覧は変更不能なコピーとし、食品とPawnの参照は同じ原物の識別だけに使う。設定offでも既存の保管個体の読取りは利用可能だが、新しい補給実行の許可を表す機能ではない。

## 競合と履歴

都市の途中操作、受取個体の輸送予約・入出庫・食品処理、食品の元持主の予約、元隊列の移動・不在・別地点をそれぞれ表示する。同時に複数の原因があるときは一つへ潰さない。照会可能でも、食品候補がゼロである場合がある。

食品のsource IDとcargo IDを、取消・到着・返却を含む全物理輸送履歴に照合する。旅用食品も除外しない。古い数量と現在数量が異なっても輸送履歴を解放・書換えず、一致した食品を保守的に候補外とする。将来の受入証が実装されるまでは、輸送が終わっただけで貨物を生活用食品へ自動変換しない。

日英画面は固定の注意文で「食品はまだ移せない」「凍結保管で生活は未実装」と説明する。長名と複数理由は実際の翻訳文を測って折り返し、一覧をスクロールする。内部IDを通常表示やtooltipへ露出しない。

## 確認範囲と限界

通常入力は人間・動物が保管中の `INH_MaintenanceResumed`、都市競合入力は `INH_DelegatedUiCityLock` を使う。`INH_MaintenanceStopped` は両個体とも返還済みなので、正経路の証拠に使わない。

照会の反復前後でCore全レコード・ID連番、完全なColony payload、元個体の生体状態・needs・装備・所持品、食品のID・数量・所有・metadata、inventory cache、使用済み証と時計が変わらないことを比較する。元隊列の現物食品の一覧、食べ手ごとの本体栄養、Coreの日需要、全履歴一致を別々に照合する。fixtureに現存する履歴食品が元隊列外にある場合、その食品を作成・移動して成功例を増やさず、実証できていない正の履歴一致を明記する。

通常と都市競合を基本ゲーム／四DLCで実行し、通常・都市競合の日英描画6と元の管理画面3を主担当が目視した。画面描画と実マウス操作は別の結果として記録する。全競合段階、特殊食品・遺伝子、未登録source、最小解像度、長期性能と第三者MOD互換は網羅したとは扱わない。

実際の食品移管には専用の準備・適用・確定journalと保存検査が必要である。候補確認の成功は、後で数量や所有が変わった食品を移せる証拠にはならない。食品補給、生活時計、飢餓・治療、生産・共有倉庫、代替隊列は [生活への計画](P04DelegatedLifePlan.md) の後続工程として残す。APIの副作用は [本体調査](P04DelegatedSupplyNativeApi.md)、実行契約は [補給レビュー](P04DelegatedSupplyReview.md)、候補照会と画面の静的レビューは [候補確認レビュー](P04DelegatedSupplyPreviewReview.md) を参照する。
