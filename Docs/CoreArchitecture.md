## 1. 先に固定する不変条件

1. 都市、地区、人物、物資、部隊、輸送は、一つのセーブ内で恒久IDを持つ。再訪、移動、占領、保存再開で付け直さない。
2. 一つの都市の管理国は同時に一つ。文化、居住者の所属、個体の保管場所、政治上の加入先を管理国と混同しない。
3. 人物・物資・軍の同じ範囲を実マップと抽象世界の双方で更新しない。切替中は当該範囲の更新を止め、無関係な都市活動は続ける。
4. 予約は物資を増やさない。在庫、予約、輸送中を別々の物資として合計しない。
5. 入植者・動物は元の個体状態を保持する。個体の名前や種族だけから複製を作って「移管」としない。
6. 同じ操作ID・同じ内容の再実行は、最初に確定した結果を返す。同じIDで異なる内容は拒否する。
7. 占領・到着・市場退出・報酬・税・部隊分割は、確認された原因に一つの確定結果を結び付ける。再訪・読込を補充や収入の原因にしない。
8. 未導入モジュールの型・定義を必須参照しない。文化単独、Core＋Colony、Core＋Worldで機能境界を維持する。
9. 読込時に不整合を見つけても、欠落物資・人物を推測で増やして整合させない。該当処理を保留し、原因とIDを記録する。
10. 敗戦した詳細都市は、残存建築・個体・物資を保持して同じ都市IDで奪還する。NPC都市の簡略生成で置き換えない。

## 2. 命名と識別子

### 2.1 配布・コード・定義

| 対象 | 規則 |
|---|---|
| Core packageId | `inheritance.core`。P01と合意済み |
| 他モジュールpackageId | `inheritance.world`、`inheritance.colony`等、下表の識別子を小文字で固定 |
| Core Assembly・名前空間 | `Inheritance.Core`。他は `Inheritance.World` 等 |
| 定義名 | `INH_<Module>_<Culture任意>_<SemanticName>`。翻訳表示名とは独立 |
| 文化キー | `starmound` 星墓、`irontree` 鉄樹、`forge` 炉、`whitecrown` 白冠、`tidering` 潮環、`skymark` 空標 |
| モジュールID | packageIdと同じ。表示名変更で変えない |

Def名とpackageIdは公開後に安易に改名しない。改名する場合は保存移行表と旧名からの解決経路を必要とする。文化キーは種族パックの存在を意味しない。Coreはキーと登録メタデータを扱い、六国家の生成や政治行動はWorldに置く。

### 2.2 セーブ内の実体ID

形式は `inh:<saveScopeId>:<kind>:<sequence>`。`saveScopeId`はP01のSaveHeaderが保存するGUIDを引き継ぎ、ID文字列表現ではハイフンを除いた小文字32桁を使う。`sequence`は正の64ビット単調連番を十進表記する。発行器と次番号をCoreの保存対象にする。番号を再利用せず、枯渇・重複は発行停止として扱う。通常の「名前を付けて保存」は名前空間を保持する。別セーブ間で資産を移植する機能は初期版の範囲外。

| kind | 対象・寿命 |
|---|---|
| `community` | プレイヤー共同体。最後の都市を失っても生存者がいれば維持 |
| `polity` | 国家等の政治主体。実ゲームの派閥参照とは対応表で接続 |
| `city` | NPC都市、直接都市、委任拠点、再訪する失陥都市。移管で不変 |
| `district` | 都市内の地区。同じ市場への再訪で不変 |
| `person` | 個体。移動・捕虜化・死亡で変えず、死亡状態を保持 |
| `animal` | 動物個体。人物と同じ保管・移動原則 |
| `lot` | 分離して会計する物資ロット。分割・統合の履歴を持つ |
| `unit` | 部隊。分割時は親子関係のある別IDを発行 |
| `shipment` | 輸送便。出発・到着・返送でも同じ便を追跡 |
| `reservation` | 拠点内の予約。解放後の再予約は別ID |
| `lease` | 地区・部隊等を詳細化する更新責任の貸出記録 |
| `operation` | 台帳操作。操作結果が不明でも新IDで再試行しない |

追加kindは保存版と契約変更として統合担当が登録する。都市名、座標、タイル番号、配列位置、ゲーム上の一時マップID、オブジェクトのメモリアドレスを恒久IDにしない。

世界生成の再現性は別に管理する。生成順序を固定し、`worldSeed / generationVersion / settingsDigest / cultureKey / settlementOrdinal`から作る生成キーを都市に記録する。同じシードと設定で地理・構成を再現する一方、別々の新規セーブは別の名前空間を持つ。生成キーの重複検査により同一世界の生成再処理を防ぐ。

## 3. 所有、所属、保管、更新責任を分ける

| 欄 | 意味 | 例 |
|---|---|---|
| `cultureKey` | 文化の由来。混成・複数文化は別リストで保持 | 鉄樹の都市を炉が占領しても鉄樹を保持 |
| `controllerPolityId` | 都市の行政・通行・税・防衛を決める現管理国 | 一都市につき一国 |
| `legalOwnerId` | 当該物資・資産を所有する主体 | 都市の国庫、プレイヤー共同体、商人等 |
| `communityId` / `affiliationId` | 人物の共同体と政治的所属 | 他国に加入してもプレイヤー共同体は保持 |
| `custody` | 個体・物資が今どこに保管されているか | 直接マップ、委任拠点保管、輸送便、地区 |
| `simulationAuthority` | 現在その対象を更新する責任主体 | 抽象世界、実マップ、移管保留 |
| `revision` | 最後に確定した変更番号 | 古い予約・占領要求の競合検出 |

人物を財産の所有欄へ押し込めない。捕虜・占領下住民・逃亡・死亡は個体の状態と拘束主体、原因操作ID、発生時刻で表す。家族・健康・装備・遺伝子・思想等は、保存された元個体に結び付けて維持する。

一個体の現在の保管先は一つ。都市への名簿所属は保管先と別にできるが、名簿を実在人数へ加算しない。実ゲームの個体参照との対応は一対一に検査する。参照が解決できなければ保留し、新しい個体を代用生成しない。

Coreの台帳は抽象物資の正本を持つ。実マップ上の実物状態はゲームの保存された実物が正本で、Coreの数量は対応・予約用の照合値にとどめる。抽象化と実体化の境界では片方だけを有効な正本にする。ゲームの物理コンテナと台帳が食い違った場合、台帳だけを根拠に実物を増減しない。

## 4. 保存する最小レコード

以下は論理スキーマであり、C#実装とRimWorld保存ラベルはP02実装時に対応を固定する。

| レコード | 必須の内容 |
|---|---|
| SaveHeader | 名前空間、Core保存版、制作版、ゲーム確認版、導入モジュールと各保存版、採用した世界モード、ID発行器、移行履歴 |
| EntityRegistry | 恒久ID、種別、提供モジュール、存在・死亡・統合済等の状態、実ゲーム参照との対応、revision |
| City | ID、文化、元所属、現管理国、管理履歴、NPC/直接/委任/占領保存の形式、規模L1〜L4、被害・復興、生産時計、税時計、地区参照 |
| District | ID、都市ID、用途、生成版、生成済状態、貸出ID、保存した個体・在庫・建築被害への参照、最後の補給時刻 |
| Polity / Community | ID、実ゲーム側対応、首都または臨時拠点ID、加入関係参照。首都不在も許容 |
| IndividualBinding | 人物/動物ID、元個体への保存参照、所属、保管先、結果状態、貸出ID、revision |
| InventoryAccount / Lot | ロットID、品目キー、数量、品質等の同一性条件、所有主体、保管先、分割元・統合先、消費・損失記録 |
| Reservation | ID、物資または個体の対象範囲、数量、元保管先、用途、便ID、状態、作成・解放操作ID |
| Shipment | ID、出発元、目的地、経路・移動手段、運搬役、積荷と予約、進行状態、所要時間、操作履歴 |
| Unit | ID、指揮主体、個体名簿または抽象人員枠、装備・補給、親子関係、位置、貸出ID、戦闘結果 |
| RepresentationLease | ID、対象範囲、貸出前の改訂番号、実マップ対応、抽象枠から除いた内訳、状態、生成・帰還操作ID |
| OperationJournal | 操作ID、原因ID、種別、完全な要求内容と照合用ハッシュ、前提revision、前後状態、各実物処理の証拠、状態、結果 |

品目キーは最低限「提供packageId＋Def名」。異なる品質、素材、耐久、装備付随状態等を無条件に同じロットへまとめない。保持が必要な情報を抽象レコードで表現できない実物は、元実物を保存保管する経路を使う。初期版ではその保管APIを確認するまで委任先へ送れる品目を限定し、未対応品目を消費・換金してごまかさない。

抽象人口は総数だけの正本を複数場所に持たない。都市に残る未実体化人口と、名簿を持つ実在個体の人数を区別する。地区へ20人を実体化する場合は20人分を抽象更新対象から差し引いた貸出枠として保持し、退出時は生存・死亡・離脱の結果で一度だけ精算する。関係や状態が確定した重要個体は、再訪時に別人物へ生成し直さない。

## 5. 物資と予約の会計

数量は品目に対応した整数単位を使う。小数相当の生産蓄積は別の整数固定精度残量にし、丸めで現物を増やさない。

- `available = usableOnHand - activeReserved`。予約は在庫の内数。
- 出発前は元拠点に実物が存在し、便は予約を参照するだけ。
- 出発時に元拠点から輸送保管へ移し、当該予約を消費済みにする。元拠点の在庫にも便の積荷にも同じ量を残さない。
- 到着時に便から受入先へ移す。受入不能なら便または到着待機場所で保管を続ける。
- 使用、腐敗、戦闘損失、徴発は原因のある減少操作。生産、採取、正当な補給・報酬は原因のある増加操作。
- 全保管先の期末量は、期首量＋生産/入手−消費/損失と一致する。所有移転・予約・積替え自体の全体増減はゼロ。

ロット分割では親の残量を減らして子IDを発行する。統合では旧IDを統合済として新しい正本または継続するロットへ参照させる。両方の数量を有効に残さない。実ゲーム側のスタック分割・統合を捕捉する経路は未確認であり、実装時に確認が必要。

## 6. 一度だけ確定する操作

### 6.1 共通操作手順

Coreを台帳書込の唯一の窓口とし、モジュールからテーブルを直接書き換えさせない。同一ゲーム処理スレッド内で直列化し、関係するIDを固定順で確保する。ゲーム本体が別のタイミングで在庫を変える場合も直前の再検査を必要とする。

1. 要求元が操作IDを一度発行し、原因レコードへ保存する。再試行はそのIDと同じ要求を使う。
2. 既存操作を検索する。確定済なら既存の結果を返す。内容不一致は拒否し、未確定ならその操作の復旧へ進む。
3. 対象のrevision、数量、保管先、貸出、権限を検査する。競合時は無変更で返し、業務判断のやり直しを求める。
4. `Prepared`として要求・前状態・意図する後状態・確保範囲を保存対象へ入れる。この状態だけで受入先の在庫を増やさない。
5. 実物を伴う場合、確認済みのゲーム側移動を行い、対象恒久ID・移動前後のコンテナ・数量・生成対象等の証拠を記録する。片方だけ成功したことを表現できる段階情報を持つ。
6. 前提を再確認し、全ての台帳後状態、結果、revision更新、処理済記録を一つの確定単位として反映して`Committed`にする。確定途中の部分スナップショットを保存しない仕組みが必要。
7. UI通知・他モジュール通知は確定後に行う。通知から報酬や在庫を直接加算しない。後続更新が必要なら原因IDに対応した別操作へ渡す。

`Prepared → Applying → Committed`を通常経路とする。副作用なしに中止できる場合だけ`Aborted`へ移す。副作用済みの取消は同一操作を巻き戻すのではなく、記録された状態から補償操作を作る。判定不能は`NeedsReconciliation`として当該資産の処理を止める。

### 6.2 保存・再開と例外

ゲームの保存とMOD台帳をまたいだデータベース的な原子性があるとは仮定しない。実装で確認できた保存呼出順・移動完了条件に応じて安全な保存点を設ける。長い移動は一括原子操作にせず、保管先の切替ごとに確定して保存できる状態機械にする。

読込後は、参照解決、実物所在の照合、未完了操作の復旧、不変条件検査の順で進め、その後に生産・戦闘・輸送の更新を再開する。

| 復旧時の証拠 | 行うこと |
|---|---|
| Prepared、全対象が移動前状態、外部副作用なし | 同じ操作を再開、または無変更で中止 |
| 実物が指定受入先に一つ存在、台帳が未確定 | 証拠を照合して台帳を後状態へ確定。再生成・再移動しない |
| 一部だけ移動済で各個体/ロットが一意に判明 | 未移動対象のみ再開するか、記録された補償を行う |
| Committed、実物と台帳が一致 | 結果を返す。再加算しない |
| 所在不明、二か所に存在、数量不一致、未知の中間状態 | 該当範囲を保留し、操作IDと証拠を診断へ残す |

移動前後の実物を確実に特定できるアダプターが完成するまでは「再開時に一度だけ」の実装合格としない。実物生成を含む詳細化も、生成物との恒久対応を同じセーブへ保持し、再開時の証拠にする。

初期版は完了操作の最低限の処理済記録を削除しない。大きい診断情報は結果を保持したまま縮小できるが、ID・要求一致判定・結果・原因対応は残す。長期版で削減する場合は遅延再試行を拒否できる境界を別途設計し、時刻だけで古い記録を消さない。

## 7. 業務ごとの状態機械

### 7.1 輸送

`Draft → Reserved → Departed → InTransit → Arrived`を基本とする。出発前の取消は`Cancelled`として予約だけを解放する。出発後は便の保管資産を持ったまま`Returning`、`Rerouted`、`Held`等へ進め、元拠点へ返金のように加算しない。襲撃・腐敗による減少は`Loss`の内訳を持つ。

出発操作と到着操作は便に保存した別々の操作IDを使う。便IDだけで全段階を同じ処理済として扱わない。部分到着・複数積荷も各対象に完了証拠を持たせる。Core＋Colonyでは通常の世界・既存勢力のまま動き、Worldの条約・国境情報がなければ標準の経路条件だけを使う。

### 7.2 占領と税・予約

占領要求には都市ID、旧管理国、新管理国、期待revision、決着時刻、戦闘/降伏/返還の原因ID、守備と資産の処遇を含める。市場警備兵の撃破だけを都市全体の決着原因にしない。

決着時刻をTとして、旧管理国に属する未精算の生産・税を半開区間 `[lastTick, T)` で一度だけ精算する。その結果と管理国変更を同じ計画に含め、T以降は新管理国が受け取る。税の権利移転と実際に遠隔へ運ぶ徴収物資を混同しない。既に出発した税輸送は便として存続し、勝手に新国庫にも加算しない。

占領計画は、未出発予約を継続・解除・保留のいずれにするか、輸送中の便を誰が受け入れるか、都市所有資産と個人資産をどう処遇するかを記録する。全物資と全人物を管理国変更だけで自動譲渡しない。適用中は関連する出発・到着を直列化する。

首都は国家側の参照。旧首都が落ちても征服国の首都にしない。旧国の臨時首都または首都不在状態を設定する。文化、元住民、思想、施設、被害は維持する。還元群の侵食は通常国家への管理移管と別操作にし、徴税・外交権を与えない。

### 7.3 地区訪問と再訪

地区の貸出は `Abstract → Materializing → Live → Reconciling → Abstract`。実物を保持した休止が必要なら、更新停止と保存形態が確認できた専用状態を追加する。単にマップを消せば抽象状態へ戻ったとは扱わない。

貸出対象は地区の人物・在庫ロット・守備枠等の明示リストに限定する。都市全体を止めない。`Live`中の対象範囲を都市の抽象生産・消費・自動戦闘から外す。対象以外から地区への正当な補給がある場合は、時刻と供給元のある輸送/供給操作として実物へ反映する。

入場は既存地区IDと状態を解決してから行う。初回生成と再訪を区別し、初期予算を初回だけ割り当てる。取引は確定時に個別操作として記録し、退出時に取引総額を再加算しない。退出では残存物資・個体・損傷と未処理差分を照合し、生存者・戦利品・死亡を元の貸出範囲へ一度だけ精算する。

滞在中の管理国変更は地区ID・個体IDを維持し、許可と外交を更新する。取引確定時は現在の権限revisionを再確認する。訪問隊は通知や退去条件を受け、管理国変更だけで消去・強制転送しない。

### 7.4 部隊の詳細戦闘

部隊から貸し出した個体と兵力枠を抽象戦闘から除外する。実マップの兵と抽象兵力を足して軍勢を算出しない。全軍を貸出した場合、その部隊の自動戦闘は停止する。

戦闘結果には、生存帰還、戦死、負傷、捕虜、離反、撤退、守備隊へ分割の各範囲を重複なく含める。守備隊への分割は子部隊IDと移った個体/兵力を確定し、親にも同数を残さない。元の抽象兵力へ全員を復元してから損失を引く方法を採らない。

### 7.5 プレイヤー詳細都市の失陥・退避

退避は選んだ個体・動物・実物を移す便または移動集団として処理する。旧街は同じcity IDで、残存状態と管理国変更を保持する。野営地・新都市は別city IDで作り、community IDは維持する。最後の都市がなくても生存共同体を消さない。

詳細都市は建物配置、設備状態、アイテム、住民、被害を保持する必要がある。NPC地区の生成テンプレートへ変換する処理は不適合。実マップを維持するか、元実物を保存した専用保管へ移すかはゲームAPI検証後の設計判断とする。初期P02では自由な休眠・復元を約束しない。

## 8. 保存版と移行

Core保存版はP01のSaveHeaderにある整数`schemaVersion`を引き継ぐ。親担当の実装報告では版1は`schemaVersion=1`と`saveScopeId`のみの最小ヘッダーで、ID発行器と移管は未実装。P02の初回契約実装は版2とし、版1→2では同じ`saveScopeId`を保持し、実在しなかった台帳は空で作成する。P01で存在しなかった都市・物資・人物を移行の名目で生成しない。実装着手時に実際の保存ラベルと既存フィールドを再照合する。

制作版（例：0.x.y）と保存スキーマ版、ゲーム版は分ける。モジュールには個別の`moduleSchemaVersion`を持たせ、Coreの共有ID・所有・操作契約の変更は必ずCore版の更新要否を検討する。

移行は旧版→新版の連続した変換にし、コピーしたテストセーブで行う。読み込んだ旧状態を直接上書きせず、変換用の状態で参照・保存不変条件を検査してから採用する。変換完了まで業務更新を開始しない。人物・数量・所有・便の移行前後を比較し、変換履歴と元版を残す。初回新版保存は別ファイルを使う運用を記録する。

未知の将来版、未対応の旧試作版、必須の保存所有モジュール欠落は、該当機能を無効にして続行するだけでは資産を失うため、対応不能として明示する。途中アンインストールは初期版で保証しない。Core側のデータが読み取れても、欠落MODのゲーム定義・個体そのものの保存可否までは保証できない。

任意DLCがない新規ゲームでは該当要素を最初から登録しない。既存セーブからDLCを除いた場合は別の互換問題であり、自動で安全に無効化できるとは扱わない。Worldの六国家モードは世界生成時に確定して保存し、CoreやColonyの導入、既存セーブの読込だけで旧勢力を削除しない。

Worldの還元群政治・脅威データとEnemyの実体提供を分ける。Enemyがない場合は還元群ユニットを参照・生成せず、未提供の実体に依存する戦闘・報酬を起動しない。未提供の内容を旧敵で無断代替しない。

Coreのコンパイル参照は任意モジュールを含めない。各モジュールがCoreの登録窓口へ機能と版を宣言する。任意連携はCoreに置く中立的な契約を介して行い、相互の具体型を必須にしない。DLC・MODの存在を確認してから関連Def・能力・画面を登録する。未導入型を参照するコードがロード時に走る構造を避ける。条件付きXML読込の具体的な書式は実ゲームの根拠を確認してから実装する。

保存レコードの提供モジュールと、更新できる唯一のサービスを登録する。WorldとColonyが同じ拠点を扱う場合も、Worldは政治・地区・占領、Colonyは生産方針・輸送計画を要求し、Coreの同じ台帳へ書き込む。両方が別の都市在庫を持たない。都市の生産更新担当は拠点ごとに一つ選び、NPCはWorld、委任プレイヤー拠点はColony、直接マップはゲーム側の実物更新を正本とする。

通知はIDと確定revisionを持つ。受信漏れしても正本から画面を再構成できる設計にする。資産変更を通知だけに依存させない。研究進行はゲームの既存研究状況を参照し、拠点別に複製しない。

## 10. 実装前に必要なゲーム側の証拠

以下は設計時点の確認要求である。Core保存土台と生存した元人物・動物の凍結保管・復帰は、後続工程で上の追記に示す範囲を確認した。死亡個体、長期委任需要、地区マップなどを同じ確認済み範囲へ含めない。後続の実ゲームコード・定義の確認で、型名、呼出条件、保存結果、対象版を記録する。

| 確認対象 | 必要な証拠・採用条件 |
|---|---|
| Core保存土台 | セーブごとの生成・読込順、参照解決後の復旧点、保存中の再入可否 |
| 個体の保管 | 通常人物・動物・死体/死亡個体の寿命、委任先保管、健康・装備・家族参照の維持 |
| 実物移動 | 受渡し成功/失敗の判断、スタック分割統合、予約との競合、元・先コンテナの保存 |
| 地区マップ | 生成・退出・破棄条件、NPC訪問とプレイヤー拠点の区別、保存再開、滞在中の時間経過 |
| 失陥した詳細都市 | 建物・アイテム・個体を保持する実際の保存経路、最後の本拠地喪失後の継続 |
| 派閥・国家対応 | 実ゲーム派閥への参照とID寿命、首都と都市管理を独立させる接続 |

APIが見つからない場合に架空の関数を補わない。ドメイン状態機械の単体検証は進められるが、実ゲームでの保存・移管の合格とは分ける。

| 試験 | 必須観察 |

| 市場入場→取引→退出→再訪 | 消費・購入分が復活しない。人物IDと被害維持。都市残部の活動は継続 |

全ての試験は期待値、実測値、ゲーム版、導入構成、保存ファイル、ログを記録する。P02設計文書の作成だけではいずれも合格としない。P02本体の保存再開・再処理検証、P03〜P06の業務統合検証、P13の旧版移行・長期負荷検証は段階を分けて報告する。
