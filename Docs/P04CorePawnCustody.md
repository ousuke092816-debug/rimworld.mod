## 実装範囲とソース

元住民・元動物をCoreが直接保持し、入庫・出庫の意図、現物移動、確定を保存する基盤を実装する。以前の0.4.5にある試験専用ホルダーから、Coreの製品ソースへ責任を移す段階である。

- [Source/Core/PawnCustody.cs](../Source/Core/PawnCustody.cs)：保管コンテナ、都市別の在籍記録、移管記録、段階API、保存と整合性検査。
- [Source/Core/CoreWorldComponent.cs](../Source/Core/CoreWorldComponent.cs)：Coreのホルダー公開、保存schema 5、既存schemaの移行、ロード後の検査と利用可否の制御。
- [Source/Core/CoreLedger.cs](../Source/Core/CoreLedger.cs)：恒久ID、Core操作、lease作成証明、書き込み制限。

通常プレイの入庫・出庫UI、輸送や委任運営との接続、保管中の需要・維持費・生産・物資出納は今回の実装範囲に含めない。製品ソースに保管APIがあることと、プレイヤーが通常操作で利用できることは別の到達点である。

## 保存する個体と所有責任

`CoreWorldComponent` は `IThingHolder` として `PawnCustody` の `ThingOwner<Pawn>` を公開する。元のPawnを深く保存し、その装備、衣服、所持品などの子ホルダーもゲーム本体の列挙処理へ渡す。新しいPawnを生成したり、名前・種族から再構成したりする方式ではない。

人物・動物のCore恒久IDと元Pawn参照を維持する。名前、性別、所属、技能・経験値、傷、年齢、思想、遺伝子、装備、衣服、所持品などは元Pawnの通常の保存処理に依存する。別プロセスでの保管再開とマップ復帰後の状態一致を両構成で確認した。生物年齢の比較許容は0〜3 tickであり、長期間の保管更新を確認した試験ではない。

都市の在籍記録は `entity / city / native / transfer` を持つ独立したCore保管表である。人物・動物のCoreレジストリを抽象個体へ変換せず、`SimulationAuthority.Physical` と元Pawnのbindingを維持する。都市への保管帰属と、ゲーム本体の物理的な所有関係を混同しない。

現物の所有先は移管段階に応じて一つだけである。通常の実マップ上のPawnは、RimWorld 1.6のマップ側 `ThingOwner` に所属する。保管中はCoreコンテナに所属し、マップに出現せず、`WorldPawns` にも二重登録しない。キャラバンなど別のホルダーからの直接入庫は提供しない。

## 元状態の保持と保管中の時間進行

この基盤はCoreから保管Pawnや保管コンテナの通常tickを実行せず、保管中の需要や健康などを代わりに更新するシミュレーションも持たない。現段階の保管は、元個体を保持したまま通常マップ・WorldPawn更新から外す、凍結保管の基盤として扱う。

保存・再開時に元の個体状態を保持する契約と、長期間の委任生活を再現する契約は異なる。食料、老化、傷の進行、治療、生産、維持費が保管中に適切に進むとは主張しない。今後の委任実装では更新主体を一つに定め、実マップの更新と委任側の更新を重複させない設計が必要である。

## 意図、現物移動、確定

公開APIは次の三段階を持つ。戻り値は移管ID、呼出モジュール、原因ID、個体ID、元Pawn負荷ID、都市ID、入庫・出庫の別、段階を持つ読み取り用snapshotである。

| 操作 | 役割 | その時点の在籍記録 |
| --- | --- | --- |
| `PrepareStore(actor, cause, entityId, cityId)` | 実マップからの入庫意図を記録する | まだ入庫を確定しない |
| `PrepareRelease(actor, cause, entityId, cityId, map, cell)` | 指定都市から指定マップ・セルへの出庫意図を記録する | 入庫時の記録を残す |
| `ApplyNative(id)` | `Applying` として元Pawnを移動する | 確定まで移管前の記録を保つ |
| `Commit(id)` | 現物の場所を検査して `Committed` にする | 入庫では追加、出庫では削除する |

Prepareでは `pawn-custody/` を付けた原因IDでCoreのcreate操作を作り、`lease` を確定する。leaseのidentityには、呼出モジュール、原因ID、個体ID、元Pawn負荷ID、都市ID、入庫・出庫の別、マップID、セル、個体の向きを長さ付きで連結したSHA-256 digestを保存する。leaseのcustodyは対象都市を指す。このleaseは移管意図の証明であり、元Pawnや在籍記録そのものではない。

意図の項目はPrepare後に変更しない。可変の移管段階は意図digestに含めないため、段階と在籍記録・現物の一致を別に検査する必要がある。digestは秘密鍵による署名ではなく、Coreの操作証明と移管記録が一致することを検査するための値である。

同じ呼出モジュール・原因IDによる同一要求は既存snapshotを返す。別の個体・都市・方向、または別の出庫先で原因IDを再利用すると拒否する。未確定の移管がある個体へ別の移管を重ねない。Core側の意図だけが存在して保管側の記録がない場合は、新たな意図を補充して修復しない。

## 保存途中の再開と失敗時の契約

`Prepared` は意図を確定した移動前、`Applying` は現物移動を開始した段階、`Committed` は在籍記録まで確定した段階である。移動済みの `Applying` では元Pawnの実際の所有先と出庫位置を照合し、同じ移管を確定できるようにする。元Pawnを複製・補充する復旧は行わない。

有効な中間保存では、入庫の `Applying` に元PawnがCoreコンテナへ移動済みでも在籍記録はまだなく、出庫の `Applying` に元Pawnがマップへ移動済みでも入庫時の在籍記録はまだ残る。この二つを、確定済みの二重所有と区別して検査する。

本APIはロード直後にすべての移管を自動確定する仕組みではない。Coreはロードした中間状態を検査し、利用可能になった後に呼出側が同じIDで `ApplyNative` と `Commit` を再開する。現物が見つからない、証明が一致しない、複数所有などの不正状態では利用・保存を拒否する。

現物移動に失敗した場合は、安全な移動元へ戻し、元Pawnを一つだけ保持した再試行可能な状態にすることを成立条件とする。マップへのspawnは例外なしで失敗する場合もあるため、戻り値と元Pawnのマップ・位置・所有先を検査する処理を実装した。移動途中の例外を扱うrollbackも実装した。今回確認した失敗例は、記録済みの出庫先を物資で塞ぎ、元Pawnの移動前に拒否する経路である。拒否後の元Pawn、Prepared段階、在籍記録、証明件数の維持と、障害物除去後の同じ移管の再開を両構成で確認した。spawn失敗や移動途中の例外を強制注入する実ゲーム試験は未実施である。

## 利用制限と保存schema 5

APIは現在の検査済みワールドのCoreに属し、利用可能なモジュールがゲームのメインスレッドから呼ぶ必要がある。ロード、保存、Core台帳の確定処理中の書き込みは拒否する。

対象はactiveな `person / animal` の物理bindingを持つ、生存した元Pawnと、activeな都市である。プレイヤー所属、非ダウン、非徴兵、精神状態なしで、赤子以外の入植者または動物であることを確認する。入庫は直接のプレイヤー本拠地マップから行い、出庫は指定都市の保管個体を利用可能なプレイヤー本拠地マップの利用可能セルへ戻す。出庫前はCoreコンテナ内の存在、所有先、非出現、WorldPawnsへの非登録を照合する。出庫先は意図に記録した向きの占有範囲全体を検査し、同じ向きを明示してspawnする。占有セルや利用できないマップへ強制的に出庫しない。

`SaveHeader.CurrentSchemaVersion` は5、producerは0.4.6である。schema 5は `inheritancePawnCustody` に元Pawnコンテナ、在籍表、移管表、件数を保存する。件数の欠落・不一致、重複ID、元Pawnのbinding違い、Core証明と意図の不一致などを検査する。

既存schema 1〜4にはそれぞれの移行経路を持ち、schema 4からは `4->5:core-pawn-custody` を記録する。旧保存から新しい元個体を生成しない。既存の任意モジュールpayloadは引き続きCore所有の文字列として保存する。schema 4のpayloadは、移行でproducer情報を更新する前に、元の保存headerのschema stampと照合する。合成schema 4のpayload正常例は、名前空間、発行器、台帳件数、恒久IDとbindingを維持し、空のCore保管へ移行した。対応stampの欠落例は拒否した。いずれも両構成で確認した。旧保存移行と回帰の個別の完了記録は証拠一覧を参照する。

ロードしたCore台帳は、マップPawnの参照解決を含むゲームロードが完了して検査が済むまで利用できない。保存直前にも保管整合性を検査する。不整合や非対応保存では保存を拒否し、ロード互換性の拒否処理はゲームを停止してメインメニューへ戻す。元の保存ファイルを書き換えて修復する方式ではない。

## ソースへ反映したレビュー修正

以下のレビュー修正を現在のソースに反映し、最終の読み取りレビューで確認した。実ゲームで確認した範囲と、まだ失敗注入で確認していない範囲は下表で分ける。

- マップ上のPawnの所有先をnativeのマップ `spawnedThings` と照合し、null所有先を前提にした判定を置き換えた。
- Coreの恒久lease IDの順序で個体別の移管履歴を検査する。確定入庫から出庫までの在籍、入出庫の交互関係、末尾だけに未確定移管があること、在籍表との完全一致を照合する。
- マップ上の中間状態でもWorldPawnsへの重複登録を拒否する。出庫意図作成・出庫適用・入庫確定に、Coreコンテナによる排他的な保管の検査を追加した。
- spawnの戻り値と現物の位置・所有先を検査し、移動処理を例外時のrollbackで囲んだ。出庫時の向きを意図digestへ保存し、セル検査とspawnに同じ向きを使用する。入庫rollbackは移動直前の向きを保存して使用する。
- schema 4のモジュールpayloadを元のheader stampに対して先に検査し、移行で不正なstampを現在の情報へ置き換えて通過させない。

## 確認した試験と残る制約

実ゲームRimWorld 1.6.4871 rev591で、基本ゲームとRoyalty・Ideology・Biotech・Odysseyの四DLCを確認する。Anomalyなし。入庫・出庫・再開は別プロセスの7段階で実行する。元住民の技能経験値を123.25に設定し、人と動物の両方へScratchを付ける。Biotech側はRobustの内在遺伝子とDarkVisionの外来遺伝子も追加し、内在・外来の区別を含めて比較する。試験開始時だけのfixture準備で、製品の保管APIが状態を付け直す処理ではない。

| 確認対象 | 確認する内容 | 本版の結果 |
| --- | --- | --- |
| 入庫・出庫の基本動作 | 元住民・元動物を入庫し、同じ恒久ID・負荷IDで出庫する | 基本／四DLCで成功 |
| 中間保存と再開 | 入庫・出庫それぞれのPrepared、現物移動後Applying、Committedを保存・再開する | 基本／四DLCで成功 |
| 個体状態 | 技能・非ゼロ経験値、両個体の傷、生物年齢、思想、内在・外来遺伝子、装備、衣服、所持品を照合する | 基本／四DLCで成功。思想・遺伝子は該当DLCのみ |
| 再実行 | 同一原因・同一IDの再実行でPawnや在籍を増やさず、異なる要求の再利用を拒否する | 基本／四DLCで成功 |
| 所有の排他性 | マップ・Core・WorldPawns・他ホルダーの重複を拒否する | 正常所有先は両構成で確認。意図的なWorldPawns二重登録の実試験は未実施 |
| 失敗とrollback | 出庫先へ物資を置いて拒否させ、同じ個体を保持したまま障害除去後に再開する | 基本／四DLCで成功。エンジン内部例外やspawn失敗の強制注入は未実施 |
| 改変保存 | 保管容器欠落、件数変更、journal欠落、stage変更、在籍記録欠落の5項目を拒否する | 基本／四DLCで成功。メニュー復帰と原本SHA256不変を確認 |
| schema 4 payload | 正常例のID・binding・件数維持、空保管への移行、stamp欠落の拒否 | 基本／四DLCで成功 |
| 旧保存・既存機能の回帰 | 旧schema 1・2・3・実版4の移行、旅程・食料・動物・不足確定・実物輸送・抽象Colonyを再開する | 基本／四DLCで成功。四DLCの六国家保存再開も成功 |

入庫意図、入庫現物移動後、入庫確定、出庫意図、出庫現物移動後、出庫確定、最終保存再開の7段階を別プロセスで確認した。Core保管の試験構成は任意のColony・WorldとAnomalyを要求しない。

実行構成、使用DLLのhash、各ログと拒否理由は [Evidence/P04CoreCustody/README.md](Evidence/P04CoreCustody/README.md) にまとめる。0.4.5の試験専用ホルダーの結果は、本版のCore保管実装の合格証拠へ置き換えない。通常UI・輸送や委任運営との接続、保管中の需要・維持費・生産、長期間の委任生活、強制spawn失敗やWorldPawns二重登録の注入は今回の確認範囲外である。
