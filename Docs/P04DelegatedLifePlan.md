## P04の本来の完了条件と、残す最終仕様

制作指示書のP04は「連絡局・台帳・輸送・最小委任」であり、直接操作2拠点＋委任1拠点で予約・出発・到着・取消・途中保存を一巡し、在庫・予約・輸送中を区別し、Core＋Colonyだけでも動くことを求める。輸送と凍結保管の一巡だけでは、設計書にある最小委任の生産・消費・個体状態を満たさない。

設計書第7節では、委任拠点は常時の詳細マップを持たず、実在する配置人員、設備、土地、供給量から一定期間ごとに生産と消費を計算する。住民の家族関係、健康、装備などを保持し、供給途絶・病気・設備損傷・襲撃・避難を扱う。日常管理には一覧・警報、備蓄目標、共同台帳、定期便、異動、食事・服装・医療・勤務方針、専門化がある。研究は本体の研究状況を共有し、遠隔在庫をその場で製造材料へ使わない。

最初の最小委任では、対応する一種類の生産、必要な実物供給、食料不足と対応する健康・治療、個体を保持した出入り、通常画面からの救援を同じ拠点で一巡させる。その後、農業村・採掘場・交易所・宿場、複数の方針・専門化・事件へ広げる。少ない対応種別で一巡を確認したことを、設計書の全機能完成へ置き換えない。

直接2〜3都市と多数の委任拠点は最終的な標準目標である。直接3＋委任5〜10はP13の負荷確認案で、固定上限や必須達成数にしない。地区訪問・詳細な救援戦闘・失陥と奪還など後続工程の仕様も残す。大都市のマップを無損失で休眠・復元する機能は本計画の近道に使わない。

## 最初に実装する一つの小さな機能

**次は「元隊列から保管個体への通常の食料補給」を先に実装する。** 一地点、一人または一頭、一種類の元食品stack、一回の移管に絞る。生産、健康変化、共有倉庫、使用済み食品の処分を同時に入れない。初心者が不足の保留理由を見た後、通常画面だけで不足を解消して既存維持費を再開できる、短い操作の一巡を得るためである。

予定する操作は「委任保管画面 → 保管個体の補給 → 現地で停止中の同じ元隊列の食品を名前と個数で選択 → 補給 → 栄養残量を確認 → 維持費を再開」である。完了待ちの食品証があれば先に既存の復旧ボタンへ案内する。元隊列が移動中・不在・別地点の場合は理由を表示し、別の隊列へ自動で切り替えない。

初回は元隊列の同行者inventoryにある、輸送貨物として予約されていない対応食品だけを扱う。保管個体は自分のinventoryで受け取る。共有食料や遠隔在庫を数値だけで足さず、同じ元Thingまたは追跡する分割片を移す。既存のimmutable貨物manifestを「納品済みだから」と書き換えて控除対象にしない。

追加API・journalは提案であり、現行にあると扱わない。意図に元入庫、都市、元隊列、食品holder、元食品ID、数量、metadata、受取個体を固定する。全量なら同じstack、部分なら元stackの残数と移した分割片IDを記録し、結合で受取IDを失わない。Preparedは全原物が移動前、Applyingは同じ原物・分割片の観測可能な中間、Committedは受取inventoryと元残数の一致とする。原因の再使用は同じ要求だけに許可し、成功済みをもう一度補給しない。

| 次回の短い検証 | 成立条件 |
| --- | --- |
| 食品1個の全量移管 | 元ID・名前・個体・食品総量を維持し、一度だけ受取inventoryへ移る |
| stackの部分移管 | 元stack残数と分割片の数量・IDを固定し、再実行で分割を増やさない |
| 意図保存・適用後保存・確定後再開 | 別プロセスで同じ意図を復旧。補給・返却・食品生成を繰り返さない |
| 競合と拒否 | 元隊列不在・移動・別地点、貨物予約、都市lock、保管移管／食品証の途中状態を原物変更前に拒否 |
| 不足解消 | 同じ保管個体に元食品を補給し、通常画面からHeld維持費を明示再開。二重請求なし |

まず基本ゲームの少数fixtureで一巡し、境界を閉じてから四DLCを同じ製品DLLで確認する。日本語・英語の描画と、実マウスによる初心者向けの補給一巡は別結果として記録する。この機能が成功しても、委任生活はまだ凍結保管＋会計のままである。

## 時計と更新責任を最初に一つにする

生活を始めた個体について、凍結保管、委任生活、元隊列／実マップの通常更新のうち、どれが当該区間を処理するかをCoreとColonyの契約で一つにする。保管コンテナにあるというだけで普通のPawn.Tickを呼ばない。必要な食料need、生物年齢、対応健康、治療、仕事を、確認した本体APIと独立した更新区間から明示適用する。関係・技能・装備・遺伝子を初期値へ付け直さない。

初回のL2では、生活開始を翌日の境界へ予約する案を採る。現在日に確定した旧維持費をもう一度徴収せず、旧会計を止める境界と新生活の最初の区間を固定するためである。当日即時開始や按分は後続の対応として残す。旧0.4.11/0.4.12の保存が読み込まれただけで生活を自動開始しない。

開始証に元入庫・元個体・都市、更新方式の版、開始tick、方針と対応資源を固定する。区間には開始／終了tick、前の確定区間、採用する食品証、適用前後の状態要約、現物への変更を固定する。可変の「最後に処理した日」だけを根拠にせず、証の鎖と確定区間から処理済みの時刻を導出する。一区間の長さは最初に固定して試験し、数値バランスと処理負荷の結果から変更版を決める。

旧維持費のDayGapは凍結会計の契約として残すが、新生活の未処理時間を無料の凍結期間へリセットしない。ロードで未処理区間を見つけたら、決まった順に上限付きで追いつくか、未処理分を保持して明示再開へ案内する。過去区間の新しい食品を現在のstackから勝手に差し引かない。処理に必要な証・物資・状態が不足する場合は保留し、未処理時刻を消さない。

設定無効は新しい生活開始の制限とし、既存生活、途中復旧、救援・返還を黙って止めない。「食料会計を停止」と「生活を停止」を同じボタンにしない。生活を凍結状態へ戻す中間操作を提供する場合は、処理済み区間と残る時刻、危険状態を確定する明示契約が必要であり、飢餓の取り消しや状態回復として扱わない。

## 健康・飢餓・治療の責任

Colonyは生活方針と仕事・医療者・供給の選択を管理し、Coreは元個体と現物の保持、食品・薬品の所有、適用証、保存検査を担当する。最終的な健康状態を元Pawnと別の抽象人口で二重計上しない。算定用snapshotは提案を作るための読取りであり、元Pawnの実際の状態と矛盾した第二の生体を永久に保存しない。

最初の生活適用は、対応個体・通常食品・限定needに絞る。現行のDailyDemandはFedを仮定した日額であり、空腹段階、年齢、傷の進行、代謝の変化を含む将来の時間積分そのものではない。食料証の同日一回契約と、生活区間で実際に満たした時間・栄養の契約を接続し、会計だけで空腹を全回復させない。薬物・特殊な摂取結果・遺伝子資源は専用の調査と保存契約を追加してから対応する。

飢餓の効果を実装する前に、現行のOriginal／Rationsが死亡個体を拒否する境界を改める必要がある。死亡に伴う元Pawn、遺体、inventory、装備、個体ID、元入庫、未完了食品証の扱いを先に定義する。死亡後の存在を欠落した生存個体として再生成せず、正当な死亡履歴と遺体の所有へ閉じる。ゲーム本来の死亡で生じる遺体はその結果として記録するが、失った旧遺体やPawnを復旧時に作り直さない。

治療は一種類の対応傷、元医療者、既存の対応薬、必要設備、所要時間に限定して始める。薬品の使用と健康効果を同じ区間に固定し、片方だけ成功した状態を保存・復旧できるようにする。効果を適用したか不明なcallback例外で、薬の追加消費や同じ治療の二度適用をしない。native健康APIの副作用・乱数・死亡・通知は、実DLLの一次調査と故障fixtureで確認する。数値を直接書き換えるだけでバニラ全体と同等になったと扱わない。

## 共有倉庫と生産で守る実物の一重化

共有倉庫は委任地点に属する専用のCore holderを候補とし、個人inventory、隊列inventory、倉庫、輸送中、使用済みの所有先を一つだけにする。具体的な保存型とAPIは未決定である。最初は預入・払出だけを実装し、食品以外へ広げる前に元ID・数量・所有・予約を照合する。残量は現物から導出し、表示用の合計を別の利用可能在庫へ足さない。

到着貨物は、完了した便の歴史的manifestを維持したまま、別の受入証で委任地点の利用可能在庫へ移す。輸送側と倉庫側で同じ数量を両方利用可能にしない。受入後に消費された元貨物を、古い便の到着replayで補充しない。予約中の貨物は生活・生産から除外し、遠隔の倉庫をその場の材料にしない。

生産は土地・設備・人員・勤務・実材料・必要研究を具体的に固定して始める。採掘・農業などの資源も、地点の根拠・資源残量／成長・作業と収穫を記録し、入庫人数だけで無制限に物資が湧く仕組みにしない。既存設備を使う場合はその元物品と稼働状態を参照し、設置条件を数値だけで無料付与しない。

製造の新しい出力は、正当な一仕事の結果として一度だけ生成・登録する。既存の消えた物資を作り直す復旧とは区別する。適用後の出力ID・数量・holderを固定し、保存再開で同じ仕事をもう一度製造しない。材料を使用したのに出力証が未確定の状態、出力があるのに受入未確定の状態、callbackで適用結果が不明な状態を個別に扱う。単なる出力欠落を、未製造の根拠にしない。

最初の一仕事では、設備消耗・品質・技能経験値などの同時変更を増やさず、必要材料と作業時間から一種類の出力を閉じる。その後に各効果を追加する。研究は本体の研究状況を参照し、委任地点ごとの別研究残高を作らない。文化設備・設計図は導入済みパックの条件として後続に接続する。

## 保存・途中復旧の共通契約

使用済み食品の退役資料は、生活と生産に共通する保存上の難所を既に示している。実DLLではScribe_Deep.LookがExposeDataの通常例外を捕捉し、SaveGameもvoidで例外を記録して戻る。したがってExposeDataでthrowするguardだけで、保存全体の原子的な拒否や前回正常保存の不変を保証しない。

L1の可逆的な移管でも保存の再入を避け、適用区間の外で整合した途中状態を保存する。L3以降の生体変化、薬品使用、死傷、生産材料処理など、元状態へ安全に戻せない変更を通常機能へ出す前には、保存入口の事前検査、一貫したsnapshot、Scribe途中の別component例外、flush／close／保存先置換の失敗を検証する。前回の正常保存のbyte/hash・再読込・再保存可能性をそれぞれ確認する。

| 状態 | 保存・再開で必要な根拠 |
| --- | --- |
| Prepared | 元所有・元状態・対象manifestと意図証が一致。別の個体・食品・薬・出力へ選び直さない |
| 適用済み／証未確定 | 同じ原物、変更結果、同じCore request/spec/resultを保持。新IDの証やnative変更を重ねず、既存証だけを明示確定する |
| Committed | 証・区間・現在の原物または正当な結果が一致。歴史的replayは読取りだけで、再支払い・治療・生産しない |
| 不確定 | 成功の根拠がない結果を正常へ補完しない。専用の保留と元意図を照合して保存できる契約が必要。再生成・再消費・二度の健康効果を禁止する |

個人、都市、倉庫、輸送、食品・薬品、生活区間の競合範囲を先に定義する。既存の都市lockを迂回して現物だけ変更しない。Coreがreadyになる前はメタデータの読み取りだけを許し、ロードで新証割当・材料消費・生活適用を開始しない。bootstrapのknown/orphan検査は新しい全履歴・control・leaseまで逆照合する。

必要な保存形式変更は工程ごとに判断し、Core7／Colony1を無条件に維持すると約束しない。旧保存を厳密に検査して空の新表へ移行し、欠けた新表を旧版扱いへ戻して自動補完しない。旧版へ戻せない境界は通常画面と配布説明に明記する。使用済み食品の退役のCore8案は別工程として維持し、生活追加の名目で先行削除しない。

## 初心者向けの画面と警報

名称中心で「現在の方式」「次にすること」「実物の供給元」を示す。凍結保管、食料会計、対応する生活委任を別の状態として表示する。「委任」だけで生活も生産も自動で完成したと誤解させない。未対応個体には、内部IDやraw例外ではなく対応できない理由を出す。

不足通知は拠点名・個人名・残り食料・危険の見込みをまとめ、「補給」「維持費／生活の未完了操作」「元個体の救援・返還」へ移動できるようにする。通知を250tickごとに繰り返さず、同じ原因・状態の間は一つに集約する。危険時の一時停止はユーザーが設定できるようにし、単なる会計停止を安全な生活停止と案内しない。

生産画面は最初に対応する一仕事だけを示し、人員、土地、設備、現地材料、食料、所要時間、出力を事前に確認できるようにする。備蓄の最低量・目標量・輸出上限は、この現地利用可能在庫へ適用する。高度な方針複製や定期便は、個別操作の意味と保存復旧が確認できてから追加する。

## 各小工程での検証とP04の判定

小工程ごとに、意図保存、現物適用後の保存、確定後の再開、同じ要求の反復、条件が変わった要求の拒否を最小fixtureで一巡する。必要な故障点だけを先に追加し、同じ保存先でゲームを並行起動しない。基本ゲームとRoyalty・Ideology・Biotech・Odysseyの確認を分け、Anomaly・World・種族パックを必須にしない。

時間を進める試験はゲーム時計を直接飛ばさず通常経路で進める。一区間、半日、数日、複数地点へ段階的に広げる。元個体・家族関係・装備・食品・薬・入力材料・出力・隊列・Core counterを照合し、DLCの追加状態は該当構成で確認する。通常の輸送・共有倉庫・生体更新が同じ時間を二重処理していないことを確認する。

長期化に伴う使用済み食品・証歴の増加は、native Thing/comp数、XML byte数、読み込み・検証時間を別々に測る。退役が未完成の段階では保持量の上限と運用可能な範囲を明示し、履歴を消して見かけ上だけ軽くしない。性能の成功はP13で実測する。

P04の最小委任を判定する場面は、Core＋Colonyの直接2拠点＋委任1拠点で、通常画面から実在する人・動物・物資を移し、現地の供給と一つの生産・消費を継続し、不足・対応健康と治療・救援の結果を同じ原物へ反映し、予約・出発・到着・取消・途中保存を一巡することである。通常の実マウス操作、日英描画、更新版移行、競合・改変保存、仕様に対する節目の人員・物資レビューをそれぞれ結果として残す。現行の保管・会計試験数を、この未実装の合格証拠として数えない。
