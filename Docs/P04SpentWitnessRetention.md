# 使用済み食品証の保持量削減：次工程の設計案

2026-10-08。**未実装の提案**。本書は0.4.11の実装・試験・配布完了を示すものではない。現行Core保存版7の実物保管・食料証を前提とし、ソース変更は行っていない。

## 現行の証明と変えてはいけないこと

- `RationDebits`の専用`ThingOwner<Thing>`に使用済み食品を保管し、通常のinventoryや輸送から取り出せない。
- 第一証は元入庫証、個人・都市・日付、元食品ID、数量、栄養、def・stuff・耐久を固定する。
- 第二証は第一証のdigestと、実際の使用済み食品IDの順序を固定する。部分消費では元stackのIDを保ち、分割した使用済みpieceを保管する。
- 適用済み・確定済みの全行と、実物の保管数・ID・所有・数量を一対一照合する。
- 確定済み食料操作は、個人が出庫・帰還した後も同じ証で無変更再実行できる。元stackは後日にさらに消費されるため、古い証で現在の元stack残量を検証しない。

削減後も第一・第二証のIDとhash、使用済みID、消費数量・栄養を変更しない。食料をinventoryへ返さず、元食品・個人を再生成せず、同じ使用済み実物を二度破棄しない。維持費の停止・再開や、生体needs・健康・技能の凍結方針とは別の操作にする。

## 選択肢

| 方針 | 減らせるもの | 限界・扱い |
|---|---|---|
| 保存形式だけ圧縮し、実物を全保持 | 保存文字列の冗長さ | native Thing・comp数は減らない。Core7互換の表示・資料整理はできても、長期の保持量削減完了とは扱えない |
| 保存上限で新しい徴収を保留 | 今後の実物増加 | 保留理由と通常画面が必要。既存証の復旧を妨げず、過去の物品を消さない暫定策。長期の連続運用を満たす解決ではない |
| 一部を残し、古い実物を証付きで破棄 | native Thing・comp数 | 残す個数が少なくても、破棄する分には下記の消去journalが必要。単なる`Remove`やstack集約で代用できない |
| 全ての対象を小さいbatchで証付き破棄 | native Thing・comp数 | 推奨する本実装候補。Core8の移行と、途中失敗の独立した保存契約を先に完成させる |

使用済みstack同士の`TryAbsorbStack`も、消える元IDとDestroyを伴う。ID一覧だけ書き換える集約は第二証を壊すため、破棄証なしの近道にはしない。

## 推奨する対象と保存版

初回は**明示操作・少量batch**で、確定済み食料操作だけを対象にする。日次維持費のTickから自動で破棄しない。対象上限・保持日数の数値は性能試験で決め、最初から無制限に処理しない。

- `RationDebitStage.Committed`かつ第二Core証もCommittedの行のみ選択する。
- Prepared／Applied／NeedsReconciliationの食料操作は除外する。
- 一つの使用済みIDは一つの破棄batchにしか割り当てない。個人が出庫済みでも、履歴と実物が一致すれば対象にできる。
- 対象はCoreが現在所有する実物に限る。他のholderから回収せず、見当たらない物品を候補に含めない。
- 最初に全候補を検査し、破棄する前に欠落・重複・所有の違いを拒否する。

Core8を新設する。旧Core7は元header、module payload、台帳、PawnCustody、全Ration証と全使用済み実物を検査した後、空の破棄journalへ移行する。旧証のhash方式を変更せず、読み込みによる物品削除・新証割当・自動圧縮はしない。

Core1〜6からの既存移行にも最後の空journal移行を追加するが、旧保存版にCore8の非空破棄データが混入していれば拒否する。Core8で破棄表・件数・必要な証が欠けた保存を、Core7扱いへ戻して補完しない。旧DLLへのdowngradeで退役実物を再生成しない。

## 消去journalと証の契約

batchに保存する最小項目は、batch ID、actor、cause、状態、件数、対象行、意図証ID、適用証ID、確定証ID、保留証IDとする。対象行には次を固定する。

1. 元RationのID・第一digest・第二証IDとidentity。
2. Ration内の行番号、元食品ID、使用済みID、数量、def・stuff・耐久、単位栄養。
3. 破棄前の専用holder所有を確認した対象manifestのhash。

日需要や食品metadataの重複保存を減らす場合も、元Rationの不変行から完全に復元し、同じcanonical manifestを計算できることを条件にする。単に最後の合計だけを保存して個別IDを失わない。

破棄用Core leaseはcity／community等への参照辺を持たせない。必要な関係はidentity hashに固定し、事前に元証を検証する。都市が未確定食料証でロック中でも、破棄の保留証が独立して保存できるようにする。

| 段階 | 保存・実物の条件 | 再実行 |
|---|---|---|
| Prepared | 不変の消去意図証が存在し、全対象実物が元ID・元数量で専用holderにある | 同じ意図と対象を選択。対象を選び直さない |
| Applied | 削除成功を記録した適用証が存在する。成功した行は使用済み実物ではなく退役metadataに対応する | 証と元行を読むだけ。成功した実物へ再度Destroyしない |
| Committed | 適用証と確定証が存在し、compact indexが全退役行と一対一対応する | 出庫後・元隊列消滅後も無変更の履歴再実行 |

`Prepared → Applied`を、単なる「実物が見当たらない」から推定しない。全量削除・partial batchとも、成功を証明した行と、未着手・不確定の行を区別する。

保存時の保存排他guardを、native操作と成功証の確定が完了するまで維持する。batch処理を別threadへ出さない。Core証だけがPrepared／Applyingの途中なら、元request/specとResultIdを検査して同じoperationを再開し、新IDを追加せず、削除を繰り返さない。

## Destroyの例外と「不明」の扱い

`Thing.Destroy`や第三者MODのcallbackは途中で例外を出す可能性がある。戻り値の成功だけでなく、呼び出した**同じ元Thing**がDestroyedになり、元holderから除かれ、別holderへ移っていないことをその場で確認する。実物が残っているのに成功証を出さない。

特に、callback例外の後に物品が既に消えている状態を、成功済みとみなして再開してはいけない。進め方を二つに分ける。

- **最小実装**：全操作成功時だけApplied証を確定する。途中例外で成功証を出せない場合は破棄を停止し、通常の保存検査を緩めない。物品の返却・再生成・再Destroyを行わない。復旧は削除前の独立した保存へ戻る方式となるため、製品として自動削除を有効にする前に、この制限を解消する。
- **本運用向け拡張**：参照辺のない`RetentionHold`証で、確認済み削除行と、不明の行・観測した失敗を固定する。不明な欠落は「正常に退役済み」へ変換せず、`Unresolved`として隔離する。保持量・数量の収支には含め、返却・補充・再削除を禁止する。専用の保留として保存できるCore8検証を追加する。

後者は、欠落を成功として受諾する仕組みではない。適用済み・保留の双方について、元消去意図・食品証・ID・行の対応を検証し、最終Disposed証を出せる条件を別途定義する。解決根拠がなければ保留を維持する。保留証の作成自体が失敗した場合も、欠落を自動補完して保存を通さない。

初回の実装では、第三者callbackの不確定状態を安全に保存できる設計が未完成なら、自動破棄を公開しない。先に基本ゲーム・四DLCの明示操作試験を行い、独立した削除前fixture・保存を保持する。

## 全体検証と保持する証拠

使用済み行の全体を、Live、CertifiedDisposed、Unresolvedの排他的な三集合へ分ける。Unresolvedは拡張を実装した場合のみ存在を許可する。

- Live行と専用holderの生きた実物が一対一対応する。
- CertifiedDisposed行と確定した消去証・compact indexが一対一対応し、同じIDの実物がどこかに残っていれば拒否する。
- Unresolved行と保留証・元消去意図が一対一対応する。不明なmissingをLiveやCertifiedDisposedに寄せない。
- 一つの元Ration行が複数集合、複数batch、別の行番号へ所属しない。
- 食品def／単位栄養／数量を用い、`全確定食料証の使用量 = Live + CertifiedDisposed + Unresolved`を照合する。個人inventory残量と混同しない。
- 元Rationの第一・第二証を削除せず、履歴のPrepare／Apply／Commit replayはcompact indexを読む。出庫・再入庫を理由に旧証を別storeへ付け替えない。
- 全Core消去・適用・確定・保留operationを対応するjournalへ逆照合し、行やbatch表を削除した保存も拒否する。

native実物を減らしても、証歴のID・行は増える。完全に一定量の保存にできるとは主張しない。native Thing・comp数、XML byte数、読み込み時間、検証時間を別々に測る。Core永久IDの再利用や、過去の日次請求の証をまとめ直して消す処理は本段階に含めない。

## 必要な実ゲーム試験

基本ゲームとRoyalty・Ideology・Biotech・Odyssey（Anomalyなし）の独立環境で行う。同じ保存先を並行起動せず、ユーザーの保存と過去の証拠・配布を変更しない。

| 系統 | 最低限の確認 |
|---|---|
| 通常段階 | Prepared保存→別process再開、Applied保存→再開、Committed再読み込み。適用・確定・完了済み再実行で追加削除・返却・ID割当なし |
| 連続履歴 | 同じ元stackの複数日消費→一部batch退役→さらに日次消費→別batch退役。全食品量・栄養・元stack IDと全元証の収支を照合 |
| 出庫・再入庫 | 旧個人の出庫後に履歴を退役。元隊列消滅後のreplay。新storeの食品証へ旧行を付け替えない |
| 停止・保留 | 維持費Stopped／Heldで処理。未確定食料・pending city lock中の対象除外と保留保存。破棄だけで維持費やPawn tickを再開しない |
| 途中故障 | 最初の削除前、一部成功後、全削除後・適用証前、適用証Prepared／Applying、compact index更新前、確定証前で停止。対象に二度Destroyを呼ばない |
| callback故障 | 元Thingが残る例外、元Thingが消えた後の例外、別holderへ移る異常。missingを正常退役として自動確定しない。対応する保留または明示したfailclosedを検証 |
| 不正保存 | 意図・適用・確定証／batch削除、件数変更、ID・数量・HP・def変更、第二証変更、別行へindex差替え、二重batch、未確定食料の混入、disposed実物の残存 |
| 旧版移行 | 0.4.10／0.4.11のCore7を厳密検査し、全実物・証・inventory・Pawn・Core counterを保持して空journalへ移行。旧版に非空消去記録が混入した保存を拒否 |
| 長期測定 | 少人数短期間→複数都市・多数日へ段階拡大。実物数・保存byte数・読み込み・検証時間と、各段階の収支を測る |

成功ログだけでなく、テスト対象DLL・元fixture・生成保存・抜粋ログのhashを保持する。不正保存の検査を弱めて途中復旧を通さない。通常生活、食料need・飢餓・健康更新、共有倉庫、輸送貨物の消費は引き続き別工程とする。
